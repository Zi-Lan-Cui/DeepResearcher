# 恢复期工具缓存方案

## 为什么要做

LangGraph checkpoint 保证的是图状态可恢复，不保证断点附近的外部工具调用恰好执行一次。服务在搜索、抓取或 Evidence 抽取完成后、下一个 checkpoint 提交前退出时，恢复后会重放所在节点。如果工具没有持久化缓存，同一次搜索、下载和 LLM 抽取就会再付一次延迟与费用。

当前只有 `SearchTool._query_cache` 进程内字典，重启即丢失；fetcher 虽已计算 `content_hash`，但没有用于持久复用；Evidence 抽取每次都会重新调用模型。因此 `AgentExecutionScope` 中的 `task_id/operation_id` 只能提供执行关联，不能解决重复付费。

目标是为外部读操作提供“按语义键至少一次执行、结果可重放”的保护，而不是把工具调用伪装成 exactly-once。

## 设计原则

1. **语义键不是执行 ID**：`run_id`、`task_id`、`tool_call_id` 用于观测和追踪；缓存键由真正决定结果的输入和实现版本组成。
2. **缓存在工具基础设施层**：Agent 和图节点仍然调用同一工具接口，不将缓存命中写入 checkpoint State。
3. **只缓存可验证的成功结果**：取消、超时、限流、5xx、解析失败和抽取异常不写正向缓存。如需负缓存，必须独立类型且使用短 TTL。
4. **版本是键的一部分**：prompt、schema、parser、provider、model 或配置改变后自然 miss，不依赖全表清空。
5. **命中不发生业务副作用**：缓存只返回值；工具仍按当前 run 生成自己的领域事件和 Evidence ID。

## 三层缓存

### L1：搜索结果

- 键：`sha256(normalized_query, provider, effective_limit, locale, search_version)`。
- 值：搜索 provider 返回的候选条目，保留标题、URL、摘要、score 和 provider 元数据；排序/去重可在命中后重做。
- TTL：默认 6 小时，配置化。搜索时效性高，不做长期永久缓存。
- 规范化：Unicode NFKC、trim、连续空白折叠、casefold；不改写词义。
- 迁移：保留当前进程内热缓存作 L0，其后读写持久层，从而兼顾单进程延迟和重启恢复。

### L2：抓取与解析结果

- 键：`sha256(canonical_url, fetch_policy_version, parser_version)`。URL 去 fragment、host 小写化；保留可能改变内容的 query string。
- 值：`final_url/content_type/title/text/blocks/content_hash/status_code/retrieved_at`，不保存 cookie、Authorization 或其他请求机密信息。
- TTL：默认 24 小时，配置化；后续可根据 HTTP `Cache-Control/ETag/Last-Modified` 细化。
- 边界：只有公开、无身份凭证的来源可进全局缓存。未来支持用户授权来源时，必须按 tenant/credential scope 隔离或禁用缓存。

### L3：Evidence 抽取结果

- 键：`sha256(content_hash, normalized_research_direction, extractor_prompt_version, evidence_schema_version, model_id, chunking_version)`。
- 不能只用 `content_hash`：同一篇文档在不同研究问题下需要抽取不同的 claim/quote。
- 值：与 run/task 无关的抽取候选（claim、quote、support、block 定位等），不直接缓存 `evidence_id/subtask_id`。命中后使用当前 task 重新校验并生成 ID，避免跨 run 泄漏执行身份。
- TTL：默认 7 天，由内容 hash 和完整版本键保证自然失效。
- 空抽取：只在全部 chunk 都成功执行且确认为 0 候选时可短期缓存；“所有 chunk 均失败”绝不能缓存为空结果。

## 持久化与调用流程

第一版使用 PostgreSQL 通用表 `tool_cache_entries`：

```text
namespace + cache_key        联合唯一键
value_json                    已验证的结果
content_hash                  可选，用于 fetch → extract 串联
created_at / expires_at
last_accessed_at / hit_count  运维与清理
schema_version
```

每层统一经过 `ToolCache` 窄接口：`get_or_compute(...)`与 `delete_expired(...)`；前者在实现内部收口双检索、single-flight 与成功写入。工具调用顺序为：

1. 由原始输入构造规范化语义键。
2. 先查 L0 内存缓存，再查 PostgreSQL。
3. 命中时反序列化为原工具返回类型，记录 `cache_hit`，并继续产生当前 run 的业务事件。
4. miss 时执行原始外部调用；只在完整成功并通过结果校验后写入。
5. 并发的同键 miss 使用单进程 per-key single-flight 合并。首版不引入分布式锁；多 Worker 冷键惊群成为实测瓶颈时，再使用 PostgreSQL advisory lock 或 Redis 机制。

`AgentExecutionScope` 的字段跟随 hit/miss 事件，用于回答“哪个 run/task 命中了什么”；它不参与语义键，否则同一工作在恢复或重新提交后无法复用。

## 实施结果（M7 已完成）

1. `ToolCache`/`NoOpToolCache` 协议与 `PostgresToolCache` 已接入 service lifespan，启动时有界清理过期项。
2. L1 保留 L0 热缓存并接 PostgreSQL；L2 缓存抓取+解析成功文档；L3 缓存 chunk 候选并在命中后重新校验/绑定。
3. `cache hit/miss/write/bypass` 与节省量进入 usage 明细和 Run 聚合，原始 value 不出现在 API/前端。
4. 以“新建工具实例+同一数据库”模拟进程重启后的恢复调用，已验证三层供应商调用数不增加。

## 验收标准

- 恢复重放同一语义调用时，搜索、抓取、抽取的外部调用计数均不增加。
- 正常新 run 的相同公开查询/来源在 TTL 内可复用，但返回的 task/Evidence ID 属于当前 run。
- prompt/schema/model/parser/provider 版本变化会导致可预期 miss。
- 取消、超时、失败和全 chunk 抽取失败不会污染正向缓存。
- 无 PostgreSQL/缓存不可用时工具可降级直连，缓存故障不改变研究正确性。
